### 2.1 TYPE A: Requirements Generation (Diagnosis-Heavy)

**When**: Product entering or in Task Clarification phase
**D-M-I-R Balance**: D=60% M=20% I=10% R=10%
**Products NOW**: P01 ARVR-SIM, P07 UAV-CAT, P08 RIT-SIM, P10 T-UAV, P11 C-DRONE, P13 NWS

```
Role: Engineering Design Architect + D-M-I-R Master
Context: ENGINEERING.md + Obsidian CONTEXT.md + project README + open-questions

═══ DIAGNOSIS (Primary — 60%) ═══

1. System Boundary Definition:
   - WHO: operator, maintainer, commander, procurer, trainer
   - WHAT: interfaces (mechanical, electrical, software, human)
   - WHERE: MIL-STD-810H condition profile for Vietnam
     (Temperature: -10/+55°C, Humidity: 95% RH,
      Salt fog, Dust, Vibration, Shock, Rain)
   - WHY: operational need → Essential Problem Statement

2. Requirements (Pahl & Beitz §5.2, 15 categories):
   Per requirement:
   - Classify: Demand (D = must have) or Wish (W = nice to have)
   - Quantify: target value ± tolerance (no vague words!)
   - Verify: T=Test, A=Analysis, I=Inspection, D=Demonstration
   - Trace: → MIL-STD-XXX / STANAG-XXXX / TCVN-XXX / ISO-XXXX

3. 5-Step Abstraction:
   Step 1) Omit wishes that limit solution space
   Step 2) Omit requirements with no function bearing
   Step 3) Transform quantitative → qualitative essence
   Step 4) Generalize to solution-neutral form
   Step 5) Formulate Essential Problem Statement

4. Archetype Scan:
   □ "Shifting Burden"? — Are we dependent on foreign system we should replace?
   □ "Eroding Goals"? — Have requirements weakened across iterations?
   □ "Fixes That Fail"? — Adding features to mask fundamental issue?

5. ODI Opportunity Landscape (if user data available):
   - What JOB is the operator HIRING this product to do?
   - Over-served needs (potential for cost reduction)?
   - Under-served needs (opportunity for differentiation)?

═══ MODELING (20%) ═══
6. System context diagram (inputs/outputs/disturbances)
7. Initial function structure sketch (overall function → sub-functions)
8. Key performance variables: Current→Target→Gap

═══ INTERVENTION (10%) ═══
9. Flag conflicts with ENGINEERING.md §5 (VKTHQ production capabilities)
10. Challenge requirements driving >50% of projected cost
11. Check D07/D08 compliance (local content, DfM for Vietnam)

═══ REFLECTION (10%) ═══
12. "Are we designing what USER needs, or what WE think they need?"
13. Check ENGINEERING.md §6 for past requirements mistakes (NEVER-XX)
14. "What assumption would change everything if wrong?"

Output: Requirements List + Essential Problem Statement + stakeholder map
```

### 2.2 TYPE B: Concept Evaluation (Modeling-Heavy)

**When**: ≥3 concept variants ready, need systematic selection
**D-M-I-R Balance**: D=25% M=40% I=25% R=10%
**Products NOW**: P04 T-USV, P06 TG, P09 TD-1300, P15 RAMS

```
Role: Engineering Design Architect + Concept Evaluation Specialist
Context: ENGINEERING.md + Requirements List + project decisions/

═══ DIAGNOSIS (25%) ═══
1. Review Essential Problem Statement — still valid?
2. Overall function → sub-function decomposition
3. Function Structure (energy/material/signal flows, P&B §6.3)
4. Archetype check: "Success to Successful"? (bias toward familiar solution?)
5. Check: Are ALL sub-functions covered? Any missing?

═══ MODELING (Primary — 40%) ═══
6. Morphological Matrix:
   - Sub-functions as rows (from function structure)
   - ≥3 working principles per row (solution-neutral!)
   - Systematic combination → ≥4 concept variants
   - Physical/geometric compatibility check between combinations

7. VDI 2225 Evaluation:
   a. Select criteria from:
      - ENGINEERING.md §8.1 standard criteria
      - Product-specific requirements (Demands = eliminators)
      - Cross-portfolio criteria (modularity, local content)
   b. Weight criteria via AHP pairwise comparison:
      - Consistency Ratio CR < 0.10 (MANDATORY)
      - If CR ≥ 0.10 → revise pairwise judgments
   c. Score each variant 0-4 per VDI 2225:
      0 = Absolutely unsatisfactory (eliminates variant)
      1 = Just tolerable (barely acceptable)
      2 = Adequate (meets basic requirement)
      3 = Good (exceeds requirement)
      4 = Very good/ideal (best technically possible)
   d. Calculate weighted utility value Wij
   e. Rank by total weighted score
   f. Sensitivity analysis: vary top 3 weights ±20%
      → Does winner change? If yes → investigate further

═══ INTERVENTION (25%) ═══
8. Document selection rationale (why THIS variant wins)
9. Document what DIDN'T win and why (for future reference)
10. Leverage scan: Are we at L12 (parameter tune) or L10 (structural choice)?
11. Check: Does winner align with ENGINEERING.md §3 architecture rules?

═══ REFLECTION (10%) ═══
12. Anti-pattern: NEVER-02 (choosing by personal preference)?
13. D-M-I-R on our evaluation: Were weights honest or biased?
14. "If we chose Variant B instead, what changes?" (test robustness)
15. Log decision → Obsidian decisions/DEC-XXX.md

Output: VDI 2225 matrix + selection rationale + sensitivity analysis
```

```

P09 TD-1300:  CONSTRAINT REDEFINED: deployment time, NOT flight endurance!

P15 RAMS:     Critical criteria: real-time AI processing latency (<100ms),

              Evaluate: edge AI (Jetson) vs cloud vs hybrid architecture.
              L3 question: "Optimize for AI accuracy or training outcome?"

## 10. D-M-I-R PRODUCT CATEGORY GUIDES

### 10.1 Simulator Products (P01, P13, P14, P15)

```
D-M-I-R EMPHASIS: D+M heavy (understanding training outcomes is complex)

UNIQUE D-M-I-R CONSIDERATIONS:
- D: User is TRAINEE, not just OPERATOR. Training effectiveness ≠ simulator fidelity
- D: "What BEHAVIOR CHANGE does training produce?" (L3 — goal clarity critical)
- M: Fidelity model: visual × physics × feedback × scenario = training transfer
- M: Diminishing returns curve: beyond what fidelity, no additional training value?
- I: L3 intervention often highest: redefine what "good simulation" means
     (hint: it's about TRAINING OUTCOME, not visual realism)
- R: Measure TRAINING EFFECTIVENESS, not just simulator specs
     Did marksmanship improve? Did decision-making improve?

COMMON ARCHETYPE: "Shifting Burden"
  Symptom: Investing in higher fidelity hardware instead of better scenarios
  Fix: Redefine success as training outcome improvement, not spec compliance

CROSS-PRODUCT SYNERGY:
  Shared scenario engine (P01↔P13), shared ballistics (P14↔P15),
  shared AI/ML pipeline (P15→P14→P01), shared AAR system (all)
```

### 10.2 Target Products (P04, P05, P08, P10)

```
D-M-I-R EMPHASIS: I heavy (operational products with clear physical constraints)

UNIQUE D-M-I-R CONSIDERATIONS:
- D: "Expendable or reusable?" changes ENTIRE design philosophy
     Expendable: optimize for COST per engagement (L3 goal)
     Reusable: optimize for RELIABILITY + recovery rate (different L3 goal)
- M: Cost-per-sortie model: (unit cost + recovery cost) / reuse count
- I: DfC dominates for expendable; DfR dominates for reusable
- I: Recovery/retrieval system IS the constraint for reusable targets
- R: Track cost-per-sortie trend over production runs

COMMON ARCHETYPE: "Eroding Goals"
  Symptom: Accepting lower RCS/IR accuracy as "good enough for training"
  Fix: Validate against actual threat systems — maintain standard

CROSS-PRODUCT SYNERGY:
  Shared autopilot+telemetry (P04↔P10), shared RCS/IR augmentation (P08↔P10),
  shared tow/launch mechanisms (P05↔P07)
```

### 10.3 Weapon Systems (P02, P03, V-SMASH family)

```
D-M-I-R EMPHASIS: ALL phases critical (full-spectrum defense product)

UNIQUE D-M-I-R CONSIDERATIONS:
- D: Safety IS the primary design driver (MIL-STD-882E Category I)
     D01: "Safety first" is DEMAND, not wish
- D: Operator under STRESS — ergonomics and training interface critical
- M: Accuracy × reliability × survivability × maintainability model
     Multiple competing objectives — VDI 2225 essential
- I: DfSafety gate: no DfSafety violation can pass ANY review
     DfR: MTBF must meet operational requirement (no single-point failure)
